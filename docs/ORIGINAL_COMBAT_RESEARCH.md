# 原版战斗与移动端布局取证

记录日期：2026-10-09。下文保留首次取证时的 M1 对照，依据本地 DemonStar 4.04 的资源和 x86 静态代码分析。首次取证未修改游戏；用户随后授权实施，M2 的落实范围见 [v0.2.0](releases/v0.2.0.md)。

实施前补核：`0x423f8f`、`0x423fcc`、`0x424009` 都限制炸弹数量小于 6 才入库；`0x424290` 读取末项，后续减少数量。`0x42418d` 起确认晶体补 2、上限 16；`0x42403e` 的护盾计数为 360。补给首次轮换等待表通常为 180，磁力为 240、超级脉冲为 250；`0x405be9` 将后续轮换计数设为 110，计数减到负值时切换。M2 使用 35 毫秒基础逻辑步长换算这些计数，实际速度仍待运行标定。

原作 `ds.exe` SHA-256：`d3d9d0205b069e5d134fdedba7b9fbd74ebcafd9785b7c9ce3d2e5ed847691b2`。下面的地址是该文件默认映像基址 `0x400000` 下的虚拟地址，仅适用于这个版本。原始资源、程序与反汇编摘录留在本地忽略目录，不随仓库分发。

## 已确认的 HUD 与初始库存

坐标单位是原作逻辑像素，不是手机物理像素；`H` 表示原作画面高度。移动端应保留信息表达和视觉风格，再适配安全区及控制区域。

| 项目 | 原版证据 | M1 差异 |
|---|---|---|
| 得分 | `0x424da6` 使用 `%07d`，一号玩家位置 `(16, 10)` | 需恢复七位数字的经典表现 |
| 生命 | `0x4239a0` 初始化总生命为 4；`0x4250be` 绘制 `生命数 - 1` 个备用战机图标，上限 6 个，起点 `(16, 20)`，间隔 9 | 当前总生命为 3，HUD 图形不同 |
| 能量 | `0x423895` 初始化为 16；`0x4251b4` 按剩余能量逐格绘制蓝色短条，起点 `(16, H-12)`，间隔 3 | 当前为 10 点能量及不同的 HUD 表现 |
| 能量条细节 | 外层 4×8、调色板索引 155；内层 2×6、索引 145；前方有小战机图标 | 应按原样式高清重绘 |
| 炸弹 | `0x423960` 初始化 3 枚；一号玩家初始三枚均为类型 0 | M1 数量相同，但只保存总数和一个类型 |
| 炸弹库存显示 | `0x425152` 遍历类型数组，在 `(16, H-21)` 起每隔 9 像素显示对应图标 | 需保存每枚炸弹类型，不能用最近拾取的类型覆盖整个库存 |

资源中的 `PLRICON1`、`PLRICON2` 和 `S_MEGA1ICON`～`S_MEGA3ICON` 均为 8×8 图标。静态消费代码 `0x424290` 读取库存最后一项，随后减少数量；仍需结合拾取行为核验完整库存规则和容量。

## 已确认的开局双发

原版不是把升级后的扇形弹数量调成 2，而是默认武器就配置了两个独立炮口。

- `0x427050` 初始化默认武器：启用槽 0、等级 0、该等级弹数 2；两项弹体类型均为 15，炮位索引分别为 0 和 1。
- 炮位表 `0x43ce28` 的前两项为 `(8, 10)` 与 `(22, 10)`。
- 发射循环 `0x4245d7`～`0x42465c` 先取主机坐标减 `(16,16)`，再加炮位偏移；因此两个发射点相对主机坐标为 `(-8,-6)` 与 `(+6,-6)`。
- 弹体模板按 `0x48` 字节排列；类型 15 绑定 `S_PDEFSHOT1A`，与默认细长弹体资源吻合。

M1 默认 `power=1`，`1 + floor(power/2)` 只生成中央一发，确实与原版不同。后续应按炮位表还原；伤害、冷却换算和全部升级形态尚未完成运行对照。

## 速度：已找到计时线索，尚未完成标定

用户观察到敌机大约快了 25%，这是一条需要验证的反馈，不是已测得的统一倍率。

- 原作 `0x419cc0` 使用性能计数器或 `timeGetTime`，换算单位为毫秒。
- 帧尾 `0x41adb0` 附近有 25 ms 检查、Sleep 及以 35 ms 为基准的等待逻辑；活动游戏还受一个速度设置值影响。这不等于“35 FPS”，也不能直接推出整场运动倍率。
- 逻辑更新 `0x41a980` 调用主机、敌机、弹体及掉落更新；运动辅助函数 `0x41e450` 按方向表累计位移。
- M1 当前采用 60 Hz，并将原始速度字段乘以 60；关卡滚动也使用这一常量。需要分别标定敌机路程、地图触发、弹速、射速，不能只把一个参数乘 0.75。

待完成的运行取证：固定相同关卡、难度、原作速度设置，记录第一波进场时刻和通过两个标记位置的时间，再核验主机射击周期及掉落轮换。此次本地窗口自动化工具初始化失败，未取得新的原作运行录像；静态分析不能替代逐帧验证。

## 已确认的移动端目标（尚未实现）

| 场景 | 布局与操作要求 |
|---|---|
| 长条手机 | 默认竖屏，不强制左右工业边框；保留经典 HUD 图标、数字和蓝色能量条，适配刘海、挖孔及手势安全区 |
| 折叠屏 / 平板 | 支持横屏、展开与窗口尺寸变化；按可用尺寸重排 HUD 和操作区，避免拉伸战机或裁掉必要战场信息 |
| 触摸操作 | 左侧虚拟摇杆，右侧 A 开火、B 炸弹；按住开火，可同时移动；摇杆驱动有上限的速度，释放归零，不能瞬移 |
| 旋转 / 调整尺寸 | 保持游戏状态；画面缩放与逻辑坐标分离，不因屏幕宽高改变敌速、弹速、碰撞或关卡触发时间 |

原作工业框的风格可以用于菜单或宽屏余量，不能为了复刻外框挤压手机战场。横屏能力需要原生方向声明与网页布局一起验收：M1 Android 当前锁定竖屏，iOS iPhone 仅声明竖屏，iPad 已声明横竖屏，但这不等于完成上述响应式布局验收。

后续验收至少覆盖长条手机竖屏、折叠屏展开/收起、平板横屏与旋转；比较相同模拟时长的敌机位置、开火结果及库存，确认尺寸变化只影响呈现与控件布局。
